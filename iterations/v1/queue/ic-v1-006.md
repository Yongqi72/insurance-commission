acceptance-criteria:
  - |-
    (源：PRD AC-14)
    intent: 打开批次详情页即可看到当前实时算出的提成汇总，按投保人分组，组内按销售人员列出票数与提成
    oracle: GET /api/commission-batches/:id/commission-summary 先调用 ruleComplete(tiers) 判断规则完整性；不完整时直接返回 {ruleComplete:false, groups:[]}（不算错误，1004 仅用于批次不存在）；完整时查询该批次内 sales_fill_source != 'unmatched' 的记录，按 policyholder 分组，组内再按 sales_name 分组计数得局部票数，每个(投保人,销售人员)组合调用 calcCommission(ticketCount, tiers) 得单价与提成；数据现查现算，不做快照，随记录变化/规则变更实时变
    example: Given "常熟"投保人下张三有 40 条已匹配记录，阶梯 (0,50]=2元、(50,100]=2.2元，When GET commission-summary，Then groups 中"常熟"分组 items 含 {salesName:"张三", ticketCount:40, commission:80}
    golden: true
  - |-
    (源：PRD AC-15)
    intent: 点击"导出"下载一份按投保人分 sheet 的 Excel 工作簿，同时归档至 OSS 并生成一条可追溯的导出记录
    oracle: GET /api/commission-batches/:id/commission-report 先查 ruleComplete(tiers)，不完整 → 返回 2002，不生成文件；完整则查询该批次全部保单记录（含未匹配），按 policyholder 分组，每个投保人一个 sheet：上方为该投保人全部明细行（客户名称/工作单号/业务类型/币种/投保人/销售[未匹配留空]/保险金额/保费/保单号），下方为销售汇总表（销售姓名/票数/提成，计算调用 calcCommission()，与 commission-summary 同一实现）+ 末行合计；生成 buffer 后先经 OssClient 上传至私有 Bucket 得 oss_key，插入一条 export_record(batch_id/oss_key/exported_at)，再把同一份 buffer 以 Content-Type=xlsx、Content-Disposition 含"{批次名}-提成报表.xlsx"流式返回；提成部分仍现查现算，不做计算结果快照
    example: Given 张三"常熟"40票、"太仓"20票，阶梯同上，When 导出，Then 常熟 sheet 销售汇总"张三 40票/提成80元"，太仓 sheet"张三 20票/提成40元"，且新增一条导出记录
    golden: true
  - |-
    (源：PRD AC-16)
    intent: 尚未回填/补录销售人员的记录仍出现在明细表里，但不影响任何人的汇总提成，也不阻塞导出
    oracle: commission-summary 与 commission-report 的分组统计均只统计 sales_fill_source != 'unmatched' 的记录；若某投保人分组下全部为未匹配，该投保人仍需出现在 groups/sheet 中（commission-summary 的 items 为空数组、subtotal=0；commission-report 该 sheet 的销售汇总表为空表，仅表头+合计0），不视为导出失败；commission-report 明细区未匹配行的"销售"列留空但仍展示该行
    example: Given "XX保险"投保人下全部 10 条记录均为 unmatched，When GET commission-summary，Then groups 中含 {policyholder:"XX保险", items:[], subtotal:0}
    golden: false

    golden: false
