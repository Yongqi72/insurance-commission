acceptance-criteria:
  - |-
    (源：PRD AC-03)
    intent: 上传 Excel 后，系统解析其中名为「账单」的 sheet，逐行导入为保单记录并归入当前批次；同一批次可重复上传多份文件
    oracle: 文件本身无法解析（非 Excel 格式/已损坏/加密保护）→ 整份文件导入失败，返回错误码 1001，提示"文件无法解析"；能解析但找不到名为「账单」的 sheet → 整份文件导入失败，返回 1001，提示"未找到「账单」sheet"；两种失败场景均不建立导入文件记录，但已上传至 OSS 的原文件不删除；批次不存在 → 1004；能定位到「账单」sheet 后跳过表头行，逐数据行按顺序（客户名称/工作单号/业务类型/币种/投保人/保险金额/保费/保单号）解析：任一字段为空、或保险金额/保费非数字 → 该行计入 failRows（行号+原因），不影响其余行；成功行批量插入保单记录，import_batch_id=当前批次、import_file_id=本次导入文件记录 id、sales_fill_source=unmatched，工作单号/保单号不做唯一校验；处理完成后插入一条导入文件记录（file_name/oss_key/imported_at/success_count/fail_count）；响应 { importFileId, fileName, successCount, failCount, failRows }
    example: Given 批次详情页，When 上传"7月账单.xlsx"（139 行全字段齐全），Then 响应 successCount=139、failCount=0，139 条保单记录落库且 import_batch_id 均为当前批次 id
    golden: false
  - |-
    (源：PRD AC-03)
    intent: 用户在导入记录列表里看到该批次全部导入历史，供确认哪次导入产生了哪些数据
    oracle: 按 batch_id 查询该批次全部导入文件记录，按 imported_at 倒序返回 [{ id, fileName, importedAt, successCount, failCount }]；批次不存在 → 1004；无导入记录时返回空数组，非报错
    example: Given 批次已先后成功导入"6月账单.xlsx"、"6月账单-补充.xlsx"两次，When GET，Then 返回顺序为"6月账单-补充.xlsx"在前
    golden: false
  - |-
    (源：PRD AC-04)
    intent: 用户可以撤销某一次导入，产生的全部保单记录随之消失
    oracle: 事务内先删除该 import_file_id 关联的全部保单记录，再删除导入文件记录本身（硬删除）；导入记录不存在 → 1004；OSS 上的原始文件不删除；删除成功后 data 为空；二次确认是前端职责，本接口收到请求即执行删除，不额外要求确认参数
    example: Given 某次导入成功导入了 50 行，When DELETE 该次导入，Then 这 50 行从 policy_record 表消失，该次导入记录本身也不再出现在 GET imports 列表里，OSS 原文件仍可通过其他有效记录访问
    golden: false

context: |-
  ImportController 用独立文件、独立路由前缀 api/commission-batches/:batchId/imports（而非往 ic-v1-002 的 commission-batch.controller.ts 里加方法），三个方法映射为 POST /、GET /、DELETE /:importId，最终解析路径与 TRD 一致；与 ic-v1-002 的 GET /api/commission-batches/:id 是不同段数的路由模式，Express 路由不会互相截获，可放心并行开发。CommissionBatch 实体（校验批次存在）、ImportFile 实体、PolicyRecord 实体扩展字段均由 ic-v1-001 建好直接 import。删除接口的级联依赖 ic-v1-001 迁移里把 sales_fill_log.policy_record_id 外键设为 ON DELETE CASCADE——本包只需在事务里删 policy_record 行，不需要额外手动清理 sales_fill_log。上传处理为同步阻塞（HTTP 请求内完成，账单 sheet 实测规模约 1300~1500 行，TRD 明确本期不做异步任务队列/进度条）。
