# PRD · v1 · insurance-commission

<!-- ac-format: intent-oracle-v1 -->

## 产品目标

用批次化的"导入 → 回填/人工补录（留痕）→ 阶梯提成实时计算 → 分投保人导出报表"流程，替代保单管理人员纯人工在 Excel 里核对提成，做到过程可控、人工干预可追责。

## 目标用户

保单管理人员（1~几人，全集团数据可见）：每月收到多份分站账单 Excel，此前需要人工逐条核对工作单号、手动数票数、按提成规则心算金额，耗时且易漏算/错算，也无法追溯"这个数是怎么算出来的"。

## 核心功能

### 功能：批次管理与 Excel 导入

**入口**：顶部导航新增「提成批次」入口 → 批次列表页 → 点击进入批次详情页（内含导入操作 + 保单记录明细列表 + 导入记录列表）

**draft-ux**：需要

**涉及实体**：提成批次、导入文件记录、保单记录

**场景描述**：保单管理人员每月创建一个批次，分多次上传各分站账单 Excel（只解析「账单」sheet），系统逐行导入保单记录归入该批次，原始文件同时归档至阿里云 OSS；导入完成后手动把批次状态标记为「已完成」；传错文件可删除该次导入撤销。

**Acceptance Criteria**：
- AC-01：创建批次
  - intent：用户填写批次名称提交后，生成新批次并进入详情页，初始状态"进行中"
  - oracle：批次名称无唯一约束（允许重名）；创建后 status 初始值固定为"进行中"
  - example：Given 批次列表页，When 新建批次填名称"2026年8月批次"提交，Then 跳转详情页，状态显示"进行中"

- AC-02：批次状态标记
  - intent：用户可在详情页把状态在「进行中/已完成」间手动切换，纯标记不影响任何数据操作
  - oracle：状态为枚举 {进行中, 已完成}；切换不锁定、不限制继续导入/删除/回填/补录/导出等任何后续操作
  - example：Given 状态"进行中"，When 点击"标记为已完成"，Then 状态变"已完成"，仍可继续上传新文件

- AC-03：向批次导入 Excel（可多次，逐行容错）
  - intent：上传 Excel 后，系统解析其中名为「账单」的 sheet，逐行导入为保单记录并归入当前批次；同一批次可重复上传多份文件
  - oracle：文件本身无法解析（非 Excel 格式/已损坏/加密保护）→ 整份文件导入失败并提示"文件无法解析"；能解析但找不到名为"账单"的 sheet → 整份文件导入失败并提示"未找到「账单」sheet"；两者都能通过则跳过表头行，逐数据行按 8 个字段处理（顺序：客户名称/工作单号/业务类型/币种/投保人/保险金额/保费/保单号）：`客户名称/工作单号/业务类型/币种/投保人/保险金额/保单号`（不含保费）任一为空，或`保险金额`非数字，或`保费`有值但非数字 → 该行判失败并跳过，不影响其余行；`保费`为空时视为该行保费缺失，允许正常导入（落库为 null）；成功行落库（`importBatchId`=当前批次，工作单号/保单号不做唯一校验）；处理完成后生成一条导入文件记录（原始文件已传 OSS，记录地址/文件名/时间/成功行数/失败行数），前端展示"成功 N 行，失败 M 行"及失败行清单（行号+原因）
  - example：Given 批次详情页，When 上传"7月账单.xlsx"，Then 逐行解析「账单」sheet，全字段齐全的行均导入成功，提示"成功导入 139 行，失败 0 行"

- AC-04：删除某次导入
  - intent：用户可在导入记录列表里删除某一次导入，撤销这次操作产生的全部保单记录
  - oracle：删除为硬删除，需二次确认；删除后该次导入关联的全部保单记录从库中移除，导入记录本身移除；OSS 上的原始文件不删除（保留可追溯上传过什么）
  - example：Given 某次导入成功导入了 50 行，When 点击删除并二次确认，Then 这 50 行从批次消失，OSS 原文件仍可访问

- AC-05：批次列表 / 保单记录明细列表
  - intent：用户能看到全部批次列表，进入详情页能看到该批次下所有保单记录明细
  - oracle：批次列表默认按创建时间倒序；空态"暂无批次，请新建"；保单明细默认按创建时间（导入顺序）升序；空态"暂无保单记录，请上传 Excel 导入"；明细列表支持按工作单号/保单号/客户名称模糊搜索
  - example：Given 新建的空批次，When 进入详情页，Then 保单记录区显示空态提示，无数据行

**明确排除**：不支持删除批次本身（仅可删除批次内某次导入）；不支持删除单条保单记录（只能整次导入撤销）；不做列顺序颠倒等高级容错，Excel 列顺序须与「账单」sheet 既定顺序一致

### 功能：销售人员回填与人工补录

**入口**：批次详情页内新增「开始回填」按钮 + 保单记录明细行内联编辑（销售人员列）

**draft-ux**：需要

**涉及实体**：保单记录、销售人员补录日志

**场景描述**：管理人员在批次详情页点"开始回填"，系统对批次内待处理记录逐条尝试调用第三方接口（本期未配置真实接口，全部落回"未匹配"，不阻塞）；管理人员在明细列表里筛出未匹配记录，逐条人工填写销售人员姓名，系统记录谁在何时改了哪条，供后续追责查证。

**Acceptance Criteria**：
- AC-06：触发批量回填（骨架，本期全部落回未匹配）
  - intent：点击"开始回填"后，系统对批次内所有待处理记录尝试按工作单号回填销售人员；本期因接口未配置，最终全部标记未匹配，操作本身不报错、不阻塞
  - oracle：遍历批次内 `salesFillSource`=未匹配 的记录，调用可配置的第三方接口地址；接口未配置/无返回/调用失败 → 保持 `salesName` 为空、`salesFillSource` 仍为未匹配；有返回且匹配到姓名 → `salesName`=返回值，`salesFillSource`=系统回填；整个操作视为成功完成（未匹配不是失败）；重复点击"开始回填"只对当前仍为未匹配的记录生效，不影响已是系统回填/人工补录的记录
  - example：Given 批次内 50 条记录均为未匹配，When 点击"开始回填"（接口未配置），Then 50 条仍为未匹配，提示"回填完成，50 条待人工补录"

- AC-07：未匹配记录筛选
  - intent：用户能在明细列表里单独筛出未匹配的记录集中处理
  - oracle：明细列表支持"回填状态"筛选（全部/未匹配/系统回填/人工补录），默认不筛选展示全部
  - example：Given 批次含 50 条未匹配 + 若干已补录，When 筛选"未匹配"，Then 仅展示未匹配的记录

- AC-08：人工补录销售人员（留痕）
  - intent：用户可对任意一条保单记录手动填写/修改销售人员姓名，保存后标记为人工补录，且系统记录本次操作人和时间
  - oracle：保存后 `salesName` 更新为填写值，`salesFillSource`=人工补录；同时新增一条补录日志（记录保单记录 id、操作人、操作时间、旧值、新值）；已是"系统回填"或"人工补录"的记录也允许再次覆盖修改，每次修改都新增一条日志，不覆盖旧日志
  - example：Given 某条记录 `salesName` 为空，When 用户填"张三"保存，Then `salesName`="张三"、状态变人工补录，生成日志（操作人=当前登录管理员，旧值=null，新值="张三"）

- AC-09：补录历史查看
  - intent：用户可以查看某条保单记录被谁改过、改了几次
  - oracle：明细行可展开/点击查看该记录关联的全部补录日志，按时间列出（操作人+时间+旧值→新值）；从未被人工修改过的记录展示空态"该记录暂无人工修改记录"

**明确排除**：真实第三方接口对接联调依赖对方接口就绪，接口就绪前只能验收"未匹配→人工补录"这条路径；接口就绪后需要另建 develop 任务做真实联调（不在本期 V1 验收范围内，是外部依赖阻塞，不是产品决定不做）；不支持批量人工补录（每次只能改一条，不支持多选统一填值）；补录日志只增不改不删，不提供编辑/删除入口

### 功能：提成阶梯规则管理

**入口**：新增独立管理页面「提成阶梯规则」

**draft-ux**：需要

**涉及实体**：提成阶梯规则、提成阶梯规则变更日志

**场景描述**：管理员在独立页面维护全集团统一的一套阶梯规则，增删改后立即对所有批次的实时提成计算生效（提成计算本身纯实时不留快照，但规则每次改动都留痕，可查是谁在什么时候把规则改成了什么）。

**Acceptance Criteria**：
- AC-10：新增/编辑/删除阶梯档位
  - intent：管理员可以对阶梯表中任意一档单独执行新增/编辑/删除，每次操作是独立请求、立即提交生效（不需要整表统一保存）
  - oracle：单价必须为正数；下限必须小于上限（最高档上限可留空表示"及以上"）；只维护唯一一套规则；删除某档、或新增/编辑后与相邻档位之间出现空隙，允许该操作本身成立、不阻止提交（空隙期间的下游影响见 AC-11/AC-14）

- AC-11：区间冲突校验（左开右闭，仅拦截重叠，允许空隙）
  - intent：保存某档时，如果新区间与已有档位重叠，阻止保存并提示；如果只是留出空隙（未紧邻），允许保存，但阶梯表在补齐前视为"不完整"，无法用于提成计算
  - oracle：区间为 `(下限, 上限]`；新增/编辑某档时，遍历其余档位，若新区间与任一其余档位存在交集（`新下限 < 其上限 且 其下限 < 新上限`）→ 拒绝保存并提示冲突档位；无重叠则允许保存（哪怕留有空隙、起点非 0、或未覆盖到无穷）；判定阶梯表"完整"的条件：全部档位按下限排序后，第一档下限 = 0，最后一档上限留空（覆盖到无穷），相邻档位首尾相接（前一档上限 = 后一档下限）——不满足任一条即为"不完整"，不阻止已发生的保存，但提成计算/导出（AC-14/AC-15）在此状态下均视为"规则不完整，无法计算"
  - example：Given 已有 (0,50]=2元、(50,100]=2.2元，When 新增 (100,150]=2.4元，Then 保存成功，此时表完整（覆盖 0 到无穷）；When 改为新增 (60,150]=2.4元（与 (50,100] 重叠），Then 保存失败，提示与 (50,100] 冲突

- AC-12：查看当前完整阶梯表
  - intent：一目了然看到当前阶梯表，以及表当前是否完整可用
  - oracle：按下限升序展示；无任何规则时空态"暂未配置提成规则"；有规则但不完整（存在空隙/未覆盖 0 或无穷）时，列表顶部展示提示"规则不完整（存在空隙），提成计算暂不可用"；完整时不展示该提示

- AC-13：规则修改历史查看
  - intent：用户可查看阶梯规则的完整修改历史
  - oracle：每次新增/编辑/删除某档位，系统生成一条变更日志（操作人/操作时间/操作类型/变更前/变更后）；管理页面提供"查看历史"入口按时间倒序列出，日志只增不改不删；规则从未变更过时展示空态"暂无变更记录"

**明确排除**：不支持"回滚到历史某版本"（要改回去需手动重新编辑成目标值，系统会生成新的变更记录）；不支持多套规则并存/按分站或业务类型差异化定价

### 功能：提成报表导出

**入口**：批次详情页新增「提成汇总」区块（实时展示）+「导出」按钮

**draft-ux**：需要

**涉及实体**：导出记录

**场景描述**：批次详情页实时展示按投保人分组的提成汇总（每个投保人下，各销售人员的票数与提成——用该投保人下的**局部票数**去阶梯规则里定档算单价，不跨投保人合并统计）；管理人员确认无误后点击导出，生成按投保人分 sheet 的 Excel，每个 sheet 上方是保单明细、下方是销售汇总；生成的文件同时归档到 OSS，管理人员可随时在"导出历史"里查看过往导出记录并重新下载原文件。

**Acceptance Criteria**：
- AC-14：批次详情页实时预览提成汇总
  - intent：打开批次详情页即可看到当前实时算出的提成汇总，按投保人分组，组内按销售人员列出票数与提成
  - oracle：仅统计已有 `salesName` 的记录；对每个投保人分组内，按销售人员分组计票数（局部票数）；用局部票数在阶梯规则里查档定单价（左开右闭）；提成=局部票数×局部单价；未配置阶梯规则、或规则存在但不完整（见 AC-11 完整性定义）时均显示"未配置规则，无法计算"；数据现查现算，随记录变化/规则变更实时变

- AC-15：手动导出提成报表 Excel
  - intent：点击"导出"下载一份按投保人分 sheet 的 Excel 工作簿
  - oracle：批次内每个出现过的投保人值各生成一个 sheet；sheet 上方为该投保人下全部保单明细行（客户名称/工作单号/业务类型/币种/投保人/销售/保险金额/保费/保单号，未匹配记录"销售"列留空）；下方为"销售汇总"表（销售姓名/票数/提成，算法同 AC-14）+ 末行为该 sheet 提成合计；提成汇总部分仍现查现算生成（不做计算结果快照，历史报表数字仍会随规则变更/补录而变化，这条风险不变）；生成的 Excel 文件本身额外上传至 OSS 存档，并记录一条导出记录（批次、OSS 地址、导出时间）
  - example：Given 张三常熟 40 票、太仓 20 票，阶梯 (0,50]=2元、(50,100]=2.2元，When 导出，Then 常熟 sheet 汇总：张三 40票/提成80元；太仓 sheet 汇总：张三 20票/提成40元

- AC-16：未匹配记录不计入销售汇总
  - intent：尚未回填/补录销售人员的记录仍出现在明细表里，但不影响任何人的汇总提成，也不阻塞导出
  - oracle：明细行销售列为空，不参与任何分组统计；若某投保人 sheet 下全部记录都未匹配，该 sheet 的销售汇总表为空表（仅表头+合计 0），并展示提示"当前没有已确认销售人员的记录"，不视为导出失败

- AC-17：查看导出历史
  - intent：用户可以在批次详情页查看该批次历史上导出过的报表记录，并重新下载
  - oracle：提供"导出历史"入口（右侧抽屉，同 AC-09/AC-13 的历史类信息呈现范式），按导出时间倒序列出该批次全部导出记录；每条可点击重新下载对应 OSS 文件（后端生成新的签名 URL，不重新计算报表内容）；无导出记录时展示空态"暂无导出记录"

**明确排除**：不支持按其他维度（非投保人）重新分 sheet；只支持导出 Excel(.xlsx)，不支持 PDF/CSV

## 用户故事

- 作为保单管理人员，我希望能创建一个批次并分多次上传各分站的账单 Excel，这样即使账单文件是陆续收到的也能归到同一批统一处理。
- 作为保单管理人员，我希望能对回填不到销售人员的保单记录手动补录并留痕，这样出了争议能查清是谁在什么时候填的。
- 作为保单管理人员，我希望能维护统一的提成阶梯规则，这样规则变了也能立即反映到所有批次的提成计算里，还能查到规则改动历史。
- 作为保单管理人员，我希望能导出按投保人分 sheet 的提成报表，这样不用再手动在 Excel 里核对每个分站每个销售的提成。
- 作为保单管理人员，我希望传错文件时能撤销某次导入，这样不用担心一次操作失误搞乱整个批次。

## MVP 边界

- 不做真实第三方接口联调——本期只留调用骨架，验收按"全靠人工补录"路径走；接口就绪后另建 develop 任务对接（外部依赖阻塞，非产品决定不做）
- 不做多角色权限差异——仍是单一管理员账号
- 不做投保人/分站名称归一化清洗——脏数据（如"太仓贝斯达"）原样入库、原样分 sheet
- 不做批次状态自动流转——状态由操作人员手动标记
- 不做提成计算结果快照/版本留存——纯实时计算，历史报表数字会随规则变更/补录而变化（已告知风险，用户确认接受）
- 不支持删除批次本身、不支持删除单条保单记录（只能整次导入撤销）
- 不支持批量人工补录、不支持阶梯规则回滚到历史版本、不支持多套阶梯规则并存
