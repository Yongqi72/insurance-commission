description: |-
  当前状态 → 期望状态：`PolicyRecordQueryService.findPage()` 的 keyword 搜索用
  `Like(\`%${keyword}%\`)` 直接拼接用户输入，未转义 SQL 的 LIKE 通配符本身（`%`/`_`）；
  工作单号/保单号等业务单据号里天然可能出现下划线（如 "WO_2026_001"），此时 `_` 会被
  数据库当成"匹配任意单字符"的通配符，导致搜索 "WO_2026_001" 时把 "WOX2026X001" 这类
  完全不同的单号也误判为匹配，属过度匹配的正确性缺陷 → 转义 keyword 中的 `%`/`_`/转义符
  本身后再拼进 LIKE 模式，恢复字面量匹配语义；顺带补齐两处已挂账的测试覆盖缺口
  （`policy-record.e2e-spec.ts` 被弱化的"空列表"断言、keyword+fillStatus 组合筛选缺失用例）。

  "全部能修的都修"指示一并处理，因三者都落在同一查询方法/同一批 e2e 用例范围内，
  合并为一个任务包。转义方案：用 TypeORM 的 `Raw()` 操作符替代 `Like()`，因为 `Like()`
  helper 不支持自定义 ESCAPE 子句；`Raw()` 里用参数绑定（而非拼进 SQL 文本）传入转义后的
  keyword 与转义字符本身，避免 MySQL/SQLite 对字符串字面量里反斜杠的解析差异（MySQL 默认
  将 `\` 视为字符串转义符，SQLite 默认不视为，若把 `ESCAPE '\\'` 写死进 SQL 文本会在两种
  驱动下产生不同的实际转义字符语义，参数绑定方式规避了这个跨驱动差异）。已跑
